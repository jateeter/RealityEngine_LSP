## Why this is a pointer

`INTEGRATION_ARCHITECTURE.md` defines the provider-neutral integration model —
the registry, the source mapper, the trigger envelope dispatcher, the dispatch
ledger, completion ingest, the MCP gateway, and the shape each provider adapter
takes. Every Perception Engine implements it, so it has to say the same thing to
all of them.

It was forked. Three near-identical copies existed — `RealityEngine_CI/docs/`,
`RealityEngine_CPP/docs/` and this one — differing by roughly a kilobyte each,
and the differences were not editorial. This copy and the C++ one carried the
`carekit` integration kind and a CareKit adapter section the master did not have;
the master carried the canonical Ollama model default and precedence rules
neither copy had. Neither was a superset, so a reader could not have known which
to trust.

This copy also carried a section headed **"## C++ Status"**, describing another
runtime's implementation slice inside the Lisp repository's documentation. That
is what a fork looks like once it has been copied a second time: the drift stops
being a disagreement and becomes an artefact nobody is reading closely enough to
notice.

Governance has one home. `RealityEngine_CI` holds `SURFACE_SPEC.md`,
`MACHINE_CONCEPT.md`, `ARBITER_ARCHITECTURE.md`, `DEPLOYMENT_CONTRACT.md`, the
`docs/*_CONTRACT.md` files and this; `scripts/check-surface-specs.sh` enforces
that each has exactly one master and that every pointer is still a pointer.

## What this repository still owns

Its implementation of the integration model — `src/perception-service.lisp`,
`src/perception.lisp`, `src/mqtt-bridge.lisp` and the CLI surface in
`src/cli.lisp` — and `docs/HEALTHKIT_SPEZI_BRIDGE.md`, its device-bridge
document.

The provider configuration and evidence the master does not carry live in the
worked instances it lists, and the rules those instances obey are in
`RealityEngine_CI/docs/EXTERNAL_INTEGRATION_CONTRACT.md`.
